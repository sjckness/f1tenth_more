## 0. Fix round 1 (manager review: 3 major, 4 minor issues)

All three major issues were in host scripts that run on the car, not in the image. Each one
was proven against the real Docker 29.5.3 CLI or against the fakes. The fakes now print
what Docker 29 prints (measured on linus); the new tests fail against the round-1 code
(checked by putting the three bugs back into a scratch copy: 24 failures, all of them on
the restored bugs or on files missing from the partial copy).

| Issue | Fix |
|---|---|
| **f1tenth_ctl_car** refused in native mode: it matched Docker's texts case-sensitively, and Docker 29 prints `error: no such object: …` / `failed to connect to the docker API …` | Exit codes decide. `docker inspect --type container` first (it covers the running case in one call: state + role). Only when that fails, `docker ps -a --filter name=f1tenth_car --format {{.Names}}` with an **exact** name match: rc 0 without the name = absent → native; with the name = refused (it exists but cannot be read); rc ≠ 0 = Docker did not answer, and only then the text decides, case-insensitively: "cannot connect to the docker daemon" / "failed to connect to the docker api" → native (daemon down), anything else, for example permission denied → refused. Real CLI on linus: no container → `native`; missing socket → `native`; socket with no listener → `native`; socket without permission → refused. |
| **docker_orin.sh** `down` / `status` broke with no container: Docker 29's failed `inspect -f` prints an empty stdout line, so `|| echo absent` gave `"\nabsent"` | `ctr_state` = `docker ps -a --filter name=f1tenth_car --format '{{.Names}} {{.State}}'` + an exact name match (`absent` when it is not there). Docker not answering is an error (says why, exit 1), never "absent". `ctr_health` and `ctr_role` are exit-code based, with `--type container`. Real CLI: `down` → "does not exist", leftovers none, history line, rc 0; `status` → rc 3; daemon down → rc 1 "cannot ask Docker". |
| **stack_mode container** reported success after a no-op `systemctl start` on a stale "active (exited)" unit | If the unit is still active, it is stopped first (its ExecStop `down` now finds no container and only reports leftovers), then started. Afterwards, in both paths (unit and `docker_orin up`), f1tenth_car must be **running with role car**, else FAILED ("the car has NO stack now"). Docker not answering fails the switch **before** the native side is touched. `status` flags a stale unit. |
| Dockerfile: the gateway venv without `--ignore-installed` | Added (`--no-deps --ignore-installed --only-binary=:all:`); a snippet test pins the flags. |
| User unit at boot cannot order after docker.service / jtop | `ExecStartPre=%h/.local/bin/docker_orin wait-host`: it waits until dockerd answers and `/run/jtop.sock` is a socket (`F1T_WAIT_HOST_S`, 120 s), returns at once on a running system, and fails with the missing piece named plus a history line. |
| `stack_mode status`: "inactive (not-found\nnot installed)" | Keeps the printed word once (`not-found` → "not installed"). |
| `docker_orin up --archive` / `--autostart` as the last word exited 1 silently | Exit 2 with a usage line; the same for `logs -n` and for an unknown `down` option. |
| Informational: wrapper overhead (P10 e-stop gate) | Container side: 2 Docker calls (inspect + exec), as before. Native side: inspect + ps. Measured in P8 (section 5). |
| Found while re-running the probes: `docker_orin restart --dry-run` passed `--dry-run` to `up` only, so its `down` half stopped a running container for real | `--dry-run` reaches both halves; a dry restart of a running container stops nothing and ends in up's "already runs" (exit 1). |
| Same empty-line form in `docker_orin status`'s pin line (`$(docker image inspect -f … \|\| echo missing)`; Docker 29 also prints the empty line for a missing image) | Exit-code based; a missing tag prints "WARNING: the tag is not present". The fake's `image inspect` now fails the way Docker 29 does. |

Also: `--type container` on every `docker inspect` of f1tenth_car (guard, banner, uninstall,
docker_orin, stack_mode), so an image, volume or network with that name can never answer.

## 2. Why the main choices (details in decisions.md)

- **Ubuntu snapshot URL**: `snapshot.ubuntu.com/ubuntu-ports/` answers 401; `snapshot.ubuntu.com/ubuntu/<id>/` serves arm64 (indexes and pool). Verified by a non-root arm64 `apt-get update` on linus (47.1 MB fetched, InRelease good signature by the Ubuntu archive key, `ffmpeg` candidate `7:6.1.1-3ubuntu5`). https only → the bootstrap update skips TLS peer checks (GPG still verifies).
- **Venv lock** resolved for cp312 aarch64 against the image's system site; the bot's tested set on linus where it applies; installed `--no-deps` so the image has exactly the recorded set.
- **Wrapper**: never the native ctl while the container runs (two stacks), whatever the health.
- **down for role car** is only `docker stop`: W1's runners are tini's children, so an "everything not under the main" sweep would cut the ordered stop.
- **HF cache read-write** (plan said read-only): the Orin has no whisper model cache to mount.
- **Phase B offline contract** with P3: `src/rust/build_env.sh` must export `CMAKE_TOOLCHAIN_FILE_<triple>` → `.../osqp_offline.cmake`, paths resolved from its own location.

## 6. Open points

- RUST=build needs P3 (rclrs 0.8 port, `src/rust/build_env.sh`, vendored QDLDL,
  `osqp_offline.cmake`): until then phase B stops with a message naming the missing piece.
- W1's files are referenced by contract only (merge before P7); `docker_orin up` refuses
  without `scripts/orin/drift_check.sh` unless `--allow-drift`. W3's `docker/orin/checks/`
  is mounted by `up --harness`.
- Not verified on an Orin: snapshot.ubuntu.com reachability from there, the groups of the
  real base image (set_gid fails loudly on a collision), every build check, health, devices.
- main-jazzy-rust pins ackermann_mux `42b7cd70` (origin/humble-jetson); the D1 image had
  `b3c0b083` (branch jazzy). Recorded in the manifest, not changed here.
- With `--archive separate` the container's runs are not synced to linus (the trigger only
  proves the mechanism); `--archive shared` for P11.
- The native `f1tenth_ctl killall`, run by hand while the container runs, would also signal
  the container's processes (same uid, visible in the host's /proc). The wrapper, the
  banner and stack_mode keep the bot and the switch off that path.
- Boot start (P12): `ExecStartPre=docker_orin wait-host` covers dockerd and jtop coming up
  after the user manager; untested on the Orin (no reboot in P8). A user unit still cannot
  order itself after system units.
- "Daemon down → native" in the wrapper assumes containers die with dockerd (the default,
  `live-restore` off). If the Orin's `/etc/docker/daemon.json` ever sets
  `"live-restore": true`, a container could keep running while the CLI says the daemon is
  down: check `docker info --format '{{.LiveRestoreEnabled}}'` in P8 (expected `false`).
- `systemctl --user stop` of a stale unit runs its ExecStop (`docker_orin down`). That exits
  3 if the dead container left Fast DDS SHM files, and the unit then shows "failed" until the
  next start. stack_mode checks that the unit is inactive, not the stop's exit code, so the
  switch goes on.
