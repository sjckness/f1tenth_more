## Adaptations to main-jazzy (and the native car) worth knowing

- **Process control**: every process is started in its own process group and
  stopped by group; no `pkill -f` anywhere (the jazzy scripts had several). After
  each shutdown the leftovers are first AUDITED (`proc_audit.py`), then swept
  (only groups whose members are all stack processes), so a cycle starts clean
  and nothing foreign is ever signalled.
- **Nothing deleted**: run directories must be new or empty; the jazzy
  `rm -rf "$OUT_DIR"` / `rm -rf "$RUNS"` / `shutil.rmtree(dst)` are gone.
- **The stack command per side**: `CTL_ENV=<f1tenth_ctl env>` makes
  `phase5_bringup.sh` start the stack exactly as that side's f1tenth_ctl does
  (its environment, e.g. native `ROS_SUPER_CLIENT=TRUE`, and its `F1T_STACK_CMD`
  with the car profile arguments of W1's `ctl_container.env`), plus the harness
  arguments (components_config, log_dir, discovery port). `d3_side.sh` sets it.
- **FEED=live** for the stand (real drivers, no bag, no stub; the 12 s hold
  mission only with `LIVE_MISSION=1`), **FEED=bag** for linus / fallback.
- **Precheck for two sides on one host**: refuses with `f1tenth_car` running (host
  side), and with the Discovery Server port held by an invisible process
  (container side: the other side's server).
- **Main-jazzy names**: components (no `health:` section), node names and output
  topics of the isolation table, the logger's `_DEFAULT_TOPICS` (the fix-batch-1
  topic list was replaced by "every logger topic the played window carried"),
  the preflight's stub (`ackermann_to_vesc_node`), restart test components,
  `KEY_TOPICS` for rates, supervisor log strings (respawn, budget, force-kill,
  SHM sweep), the logger lock path, `mission_logger_runs_dir`.
- **Archive sync in logger_check and phase5_bringup**: captured (PATH shim +
  `F1TENTH_ARCHIVE_TRIGGER`, the latter set after `CTL_ENV` is sourced),
  never executed, and passing for the native (systemctl) and the container
  (trigger file) logger alike; the jazzy check refused where the service exists,
  i.e. on the Orin. phase5_bringup.sh got the redirect in fix round 1.
- **MPC timing**: main-jazzy's `solve_dt_sec` is node-clock time (0 under sim
  time) and there is no `SOLVE/in` log line; the gate uses the wall-clock
  receive period of `/mpc/solver_status` (`stack_probe.py stamps` beside the
  replay) and `mpc_capture_node.py`'s perf_counter solve time.
- **Replays** use each side's production launch files (`layer_replay.launch.py`,
  use_sim_time via SetParameter) and derive the played / recorded topics from the
  graph (`stack_probe.py io`, after the endpoints settled), so they cannot drift
  from either side's code; ekf_global and slam use fixed lists too, because
  robot_localization subscribes only once /clock runs; /tf is always played
  (the input bag drops the layer's own edges).
- **Humble compatibility**: Python 3.10 syntax checked for every file (static
  checks' PEP 701 rules + `ast.parse(feature_version=(3, 10))`); bag options
  probed (`--delay`, `--disable-keyboard-controls`, `--use-sim-time`); Humble's
  `ROS_LOCALHOST_ONLY` where Jazzy has `ROS_AUTOMATIC_DISCOVERY_RANGE`.

## Findings for the coordinator / the user

- **linus moved to the ROS snapshot during the run** (pref file 23:08, apt
  23:12). `ldd -r` over the main-jazzy install: `ackermann_mux` is the only
  broken binary (undefined `diagnostic_updater::Updater` constructor). W3 did not
  rebuild main-jazzy (not its worktree); the smoke used a scratch overlay of
  ackermann_mux. Main-jazzy (and every worktree) needs the CLAUDE.md clean
  rebuild (P2.5) before its stack runs on linus.
- **mission_logger_node dies with exit -2 at stack shutdown** (a second SIGINT
  hits it inside `destroy_node`; KeyboardInterrupt traceback) and leaves
  `/tmp/mission_logger.lock` with a dead pid. It is reclaimed at the next start,
  so the harness reports it and does not gate it; worth a look on main-jazzy (the
  component's launch receives SIGINT from the supervisor's `killpg` AND forwards
  it to its node).
- **The Discovery Server outlives every launch** (`sh fastdds` does not forward
  SIGINT; `fast-discovery-server` is reparented to init). By design for reuse;
  reported by the smoke gate.
- **A fresh rclpy publisher on loaded linus needed ~2.3 s to match** the logger
  (publish_mission_status.py now waits for the match, up to 20 s); the jazzy
  2 s hold lost the message.
- **Parameter snapshots of lifecycle nodes depend on timing**: two snapshots of
  the same stack differed only in parameters slam_toolbox and a viz throttle
  declare late (on configure / on the first message). Compare snapshots taken
  the same way, with the feed running, and read such differences as timing.
- **mpc_corr is pinned to cores 10,11** (`mpc_corr.launch.py`): it never starts on
  an 8-core host; the linus smoke used `CPU_REMAP=1`.

## Open issues / assumptions for W2 and P8 / P9

- W2's `compose.harness.yaml` mounts of the checkout (`$F1T_REPO`) only
  `scripts/`, `tools/` and `docker/orin/checks/` read-only and `output/`
  read-write, each at its host path, on top of compose.yaml's state mounts

  change needed.

  compose.yaml): the healthcheck `/opt/f1tenth_ws/docker/orin/container/healthcheck.sh`
  (`F1T_HEALTHCHECK`; round 0 had `/opt/f1tenth_ws/container/`, which would
  have failed P8.1 / 8.13 every cycle); the ctl env picked inside the container:
  an explicit `F1T_CONTAINER_ENV`, else the container's `F1T_CTL_ENV`
  (compose.yaml: `/opt/f1tenth_ws/src/f1tenth_ctl/config/ctl_container.env`),
  else the installed `share/f1tenth_ctl/config/ctl_container.env`;
  `$F1TENTH_ARCHIVE_TRIGGER` from that env file; the mission dirs at
  compose.yaml's mount targets (`install/share/f1tenth_behavior/missions/llm_generated`,
  `mission_videos`, ...); the host units `f1tenth-archive-trigger.path` /
  `f1tenth-archive.service`.

  headers in the image. W2's final stage (`ws`) descends from `base`
  (build-essential), `cuda` (cuda-cudart-dev-12-9, nvcc) and `zed`, so all
  three should be there; confirmed only once the first image is built (P7).
