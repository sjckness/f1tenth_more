## 2. Versions

| Component | Version | Source |
|---|---|---|
| rustc / cargo | 1.99.1 (stable, x86_64-unknown-linux-gnu) | rustup (`~/.cargo`), already present |
| **rclrs** | **=0.7.0** (pinned exactly) | crates.io |
| rosidl_runtime_rs | 0.6.x | crates.io (rclrs dependency) |
| rosidl_generator_rs | 0.4.11 (`ros-jazzy-rosidl-generator-rs`) | apt, already installed |
| colcon-cargo | 0.2.0 | pip (user) |
| colcon-ros-cargo | 0.2.0 | pip (user) |
| cargo-ament-build | 0.1.11 | `cargo install cargo-ament-build` |
| libclang | not needed (see below); `libclang1-18` runtime present, `libclang-dev` not installed | apt |

**Why rclrs 0.7.0 and not the newest 0.8.0.** Message crates are generated by
`rosidl_generator_rs` into `share/<pkg>/rust` of every interface package. The apt Jazzy packages
on linus already ship them (51 packages, e.g. `/opt/ros/jazzy/share/sensor_msgs/rust`), generated
by generator 0.4.11 against `rosidl_runtime_rs = "0.6"`. rclrs 0.8.0 depends on
`rosidl_runtime_rs 0.7` and takes messages through the new `ros-env` crate
(`[package.metadata.ros-env]`), which these generated crates do not carry
(`[package.metadata.rclrs] reexport = true`). rclrs 0.7.0 is the newest release on runtime 0.6.
Moving to 0.8 needs `ros-jazzy-rosidl-generator-rs` 0.5.0 (the apt candidate, 2026-09-11 sync)
AND every interface package regenerated with it, i.e. an apt upgrade of the ROS packages. Per the
rebuild policy in CLAUDE.md, that also means a clean rebuild of every CMake package.

**libclang.** rclrs 0.7/0.8 ship pre-generated rcl bindings per distro
(`src/rcl_bindings_generated_jazzy.rs`); their build.rs does not run bindgen. libclang-dev is
therefore not required on Jazzy; it would only be needed to regenerate bindings.

**pip, not pipx, for the colcon plugins.** colcon is installed from apt
(`python3-colcon-*`, `/usr/bin/colcon`) and finds its extensions through Python entry points in
its own interpreter's site-packages. pipx puts each tool in an isolated venv that the apt colcon
never sees, so `colcon list` would not know `ament_cargo` packages. Installed with
`pip install --user --break-system-packages colcon-cargo colcon-ros-cargo` into
`~/.local/lib/python3.12/site-packages` (PEP 668's flag; user site only, no system files).

**rosidl generator.** Already installed (`ros-jazzy-rosidl-generator-rs` 0.4.11). It hooks into
`rosidl_default_generators`, so workspace interface packages get Rust bindings automatically when
built: `install/f1tenth_messages/share/f1tenth_messages/rust` exists after a normal build. No
`ros2_rust_jazzy.repos` checkout is needed.

## 3. ros2-rust/ros2_rust#557 workaround

rclrs 0.6/0.7 contain vendored copies of `example_interfaces` and `test_msgs` (for their own
doctests) and link `libtest_msgs__rosidl_typesupport_c`/`..._generator_c`. Reproduced here: without
it, the link fails with `rust-lld: error: unable to find library -ltest_msgs__rosidl_typesupport_c`.
The issue is still open; the README workaround (merged 2026-01-26) is to declare both packages
as dependencies and have them installed.

- `example_interfaces`: apt, installed.
- `test_msgs`: **not installed and no sudo**, so built from source into an underlay matching the
  installed rcl_interfaces 2.0.3:

  ```bash
  mkdir -p ~/dev_ws/rust_underlay/src && cd ~/dev_ws/rust_underlay
  git clone --depth 1 --branch 2.0.3 https://github.com/ros2/rcl_interfaces.git src/rcl_interfaces
  git clone --depth 1 --branch jazzy https://github.com/ros2/test_interface_files.git src/test_interface_files
  source /opt/ros/jazzy/setup.bash
  colcon build --packages-select test_interface_files test_msgs     # 22 s
  ```

  With sudo, `sudo apt install ros-jazzy-test-msgs` replaces this.
- Both crates and both `<depend>`s are declared in each Rust package (Cargo.toml, package.xml).
- Build-time only: the binaries do not load libtest_msgs (rustc links with `--as-needed`), so
  the underlay is not needed at run time. `ldd` shows no test_msgs dependency.

## 4. Layout and build of the Rust packages

```
src/rust/
  Cargo.toml                     virtual workspace: members only (see below)
  Cargo.lock                     committed
  clippy.toml rustfmt.toml       tests may unwrap; edition 2021
  f1tenth_proximity_guard/       ament_cargo package: Cargo.toml + package.xml
  f1tenth_costmap_boundary_rs/   ament_cargo package
```

- colcon-cargo identifies the virtual workspace and enumerates its members; each member is an
  `ament_cargo` package (colcon-ros-cargo).
- **Members do not inherit from the workspace** (`edition.workspace = true`, `[lints] workspace
  = true`, `x.workspace = true`). cargo-ament-build installs each lib crate's manifest into
  `install/<pkg>/share/<pkg>/rust`; colcon-ros-cargo then patches the crate to that path, and
  cargo fails with "failed to find a workspace root". Versions and lints are repeated per crate.
- **colcon-ros-cargo writes `.cargo/config.toml` in the colcon workspace root** with a
  `[patch.crates-io]` entry per Rust package of every prefix in AMENT_PREFIX_PATH (56 on linus).
  Its paths are absolute and machine-specific: it is `.gitignore`d. Cargo prints "patch ... was
  not used in the crate graph" for the unused ones: noise. Do not run two colcon builds of Rust
  packages at once (both rewrite the file).
- **Building one Rust package alone** (`--packages-select f1tenth_proximity_guard`): cargo
  resolves every member of the workspace, but colcon-ros-cargo patches only the message crates
  visible to the package it builds (its dependencies plus the /opt/ros underlay). A message
  package built IN this workspace and used by another member (`f1tenth_messages`, used by
  the costmap crate) must therefore be a `<build_depend>` of every member, or that
  single-package build fails with "no matching package named `f1tenth_messages`". The guard's
  package.xml carries it, with the reason (found 2026-10-18).
- Gates used before each commit (from `src/rust`, the environment above sourced):

  ```bash
  cargo fmt --all --check
  cargo clippy --all-targets -- -D warnings      # lints: unsafe_code forbid; unwrap/expect/panic deny
  cargo test
  colcon test --packages-select f1tenth_proximity_guard f1tenth_costmap_boundary_rs
  ```

  `cargo` inside `src/rust` uses the colcon-written `.cargo/config.toml` (parent directory), so
  build the packages with colcon once first.
- `serde_json` is used with `float_roundtrip`: its default float parser is not correctly
  rounded (1 ulp), which the parity harness first reported as extraction differences.

Install result (lib/<pkg>/): `proximity_guard_node`, `proximity_guard_replay`,
`costmap_boundary_node`, `costmap_boundary_replay`.

## 5. aarch64 notes for the Thor (nothing installed there)

The Thor runs Jazzy from apt, user `andre`, `~/dev_ws/f1tenth_more`, built **without**
`--symlink-install`. Steps when the Rust nodes should run there:

1. `curl https://sh.rustup.rs -sSf | sh -s -- -y` (installs `stable-aarch64-unknown-linux-gnu`);
   rust-version 1.85 or newer.
2. `pip install --user --break-system-packages colcon-cargo colcon-ros-cargo` (same reason as on
   linus), `cargo install cargo-ament-build`.
3. Check the generator and the runtime the apt messages were generated for, which decide the rclrs version:
   `dpkg -l ros-jazzy-rosidl-generator-rs` and
   `grep rosidl_runtime_rs /opt/ros/jazzy/share/sensor_msgs/rust/Cargo.toml`.
   - 0.4.x / runtime "0.6": rclrs =0.7.0 as here, no change.
   - 0.5.x / runtime "0.7": the Thor's apt snapshot is newer than linus's. rclrs 0.7.0 will not
     build against it; that needs rclrs 0.8 and the ros-env message path (a code change in both
     crates: `use ros_env::sensor_msgs` style imports). Do not mix snapshots between machines.
   - `share/sensor_msgs/rust` missing: the generator was installed after the message packages;
     reinstall the interface packages or build them from source.
4. `test_msgs` for #557: `sudo apt install ros-jazzy-test-msgs`, or the underlay of section 3.
5. Build with `--symlink-install` (memory note: the Thor's install is a copy install; a pull alone
   changes nothing).
6. The node binaries are native aarch64 builds; cross-compiling from linus is not set up (the
   message crates link against the target's ROS libraries).
7. The parity results (bit-exact on linus) assume glibc's libm on both sides. On aarch64,
   numpy and Rust still call the same libm, but re-run `tools/rust_parity/*/` once before relying
   on it there.

Orin (Humble, docker) is out of scope: rclrs 0.7 supports Humble, but nothing here was built or
tested for it.
